# Nico-agent 架构演进方案

> 2026-10-31 基于当前源码制定。本文是目标结构和迁移顺序，不表示目录或性能能力已经实现。

## 定位

Nico-agent 是可长期扩展的本机求职 Agent。当前功能闭环已经形成，但 `career_agent` 仍是扁平包。**Python package 是发布与导入单位，不决定系统规模**；当前真正的维护问题是业务流程、HTTP、存储和外部适配的边界尚不够明确。先演进为分层的模块化单体，保留一个部署进程和同一 SQLite 数据库；各模块有稳定契约后，才可按负载和团队边界选择独立进程或服务。

目标是新增一个模型、工具、渠道或求职能力时，改动集中在对应模块，并能独立验证；不以目录数量、服务数量衡量架构质量。

## 当前源码事实

| 现有边界 | 事实与证据 | 演进原因 |
|---|---|---|
| HTTP 与应用流程 | `career_agent/main.py` 包含应用初始化、账户中间件、请求模型、聊天/面试/记忆/材料路由及流程协调 | CLI 和后续渠道难以直接复用 HTTP 之外的完整用例 |
| Agent 运行 | `career_agent/runtime.py` 已集中模型循环、工具调用、取消和结果提交；`context.py`、`events.py` 分离 | 保留同一运行内核，同时把工具授权/执行和会话用例从运行循环中划出 |
| 持久化 | `career_agent/store.py` 同时建表并处理会话、消息、面试、材料、记忆和事件 | 未来 schema 迁移与领域改动容易波及一个大文件；当前 SQLite 事务语义必须保留 |
| 模型与扩展 | `providers/`、`models.py`、`mcp.py`、`plugins.py`、`channels.py` 已有真实调用边界 | 接入新适配器可沿既有协议扩展，但渠道绑定/去重仍只在内存中 |
| 产品入口 | `career_agent/cli.py`、`static/app.js` 分别承载完整命令和前端交互 | 后续增加入口时应调用应用用例，不复制状态机 |
| 业务约束 | `skills/chat.md`、`skills/interview.md`、`tools.py`、`context.py` 定义提示词及工具可见性 | 工具声明、授权和实际执行必须保持同一快照 |

## 目标结构与依赖方向

以下是**逐步迁移后的归属**，不是一次创建空目录。仍可用一个 `career_agent` 包发布；未来若独立部署某模块，再按真实边界拆包。

```text
career_agent/
  app.py                 # 组装 Store、模型、MCP、插件、应用服务及入口
  api/                   # HTTP 路由、请求/响应模型、鉴权适配
  application/           # chat、interview、memory、materials 用例
  domain/                # 会话状态规则、授权规则、领域结果类型
  agent/                 # 运行循环、上下文、事件、工具执行
  integrations/          # providers、MCP、插件、渠道适配
  persistence/           # SQLite 连接/事务、各领域查询与迁移
  cli/                   # 命令解析、输出格式
  static/                # WebUI；视新增页面复杂度再分文件
  skills/                # 聊天和面试的版本化提示规则
tests/                   # 按用例、契约和少量端到端流程组织
```

调用方向：`api / cli / 渠道适配 → application → domain + agent 端口 → integrations / persistence`。`application` 不导入 FastAPI、argparse 或具体平台 SDK；`domain` 不导入数据库、HTTP、模型 SDK。`agent` 可依赖模型/工具的最小协议，但不依赖具体供应商。先用构造函数注入已有对象，不引入通用 DI 容器。

`chat` 与 `interview` 是两个应用用例，继续共享 Agent 运行内核。面试状态、题目和反馈由面试用例负责；运行内核只知道消息、可用工具、预算、取消和终态。账户与授权在进入用例前确定，Store 的事务仍保证版本检查和结果提交原子性。跨层使用明确的输入/输出类型；现有数据库行字典只留在持久化边界，迁移时逐个用例替换，避免全库一次性重写。

## 演进阶段

### A. 应用服务与入口解耦（首先实施）

- 从 `main.py` 和 `cli.py` 提取聊天、面试、记忆候选、材料的共享用例。HTTP 路由只做参数映射、身份绑定及响应映射；CLI 与渠道调用同一用例。
- 在请求开始时构造账户作用域的依赖，避免业务函数读取全局 `ContextVar`。保留现有 URL、CLI 命令和数据库格式。
- 完成条件：现有 API/CLI 行为测试通过；分别通过 API 和 CLI 跑通同一聊天及面试流程；应用服务可用假 Store/Provider 单独测试；无跨账户访问。

### B. 持久化边界与可升级数据结构

- 将 `store.py` 的连接/事务、会话消息、面试、材料主张、记忆候选和事件查询按职责迁移。保持同一 SQLite 连接和事务边界；对跨领域提交继续由应用用例协调，不能让拆文件破坏原子性。
- 建立显式 schema 版本及前向迁移脚本；升级前备份，迁移失败不留下半升级数据库。现有 `restore.py` 与 `auto_backup.py` 要随 schema 版本验证。
- 完成条件：旧数据库副本可升级并读取，重复启动迁移幂等，失败回滚；会话版本竞争、账户隔离、备份恢复测试通过。

### C. 可扩展的 Agent、工具与模型内核

- 在现有 `runtime.py`、`providers/`、`tools.py` 上明确一次运行的输入、事件和终态契约；工具目录与执行策略共用同一授权快照。模型适配保留供应商原生错误/用量语义。
- 先把真实选定端点接入契约验证，再按需要实现流式事件；扩展写工具前设计逐次确认和不确定执行结果，不能靠重试掩盖副作用。
- 完成条件：现有取消/迟到提交、协议、MCP 与插件测试通过；新增一个假模型或假工具只触及适配层；流式功能实施后验证中断和部分输出不会错误提交。

### D. 渠道、插件与前端扩展

- 选定第二文字渠道后，持久化渠道绑定、入站消息 ID 和投递 ID；平台适配只映射身份、消息和投递结果，复用 A 的聊天用例。
- 插件保持声明、加载、授权、调用、关闭的生命周期边界；不可信插件出现时再做进程隔离。WebUI 出现第二个较大管理界面时，将 `static/app.js` 按聊天、面试、设置与共享请求层拆分。
- 完成条件：进程重启后重复消息不重跑模型，投递重试保留 ID；插件超时不宣称已取消；现有 WebUI 流程和黑白灰约束仍通过检查。

## 性能与可靠性路线

先建立测试基线：本机 100/1,000/10,000 条消息与记忆的会话读取、上下文组装、检索、备份耗时；并发 1/4/16 个会话的吞吐、SQLite 锁等待、P50/P95 延迟、模型首响应时间与工具耗时。测试使用临时数据目录和假模型，真实端点延迟单独记录。每次优化给出优化前后数据和正确性测试。

优先级：检查查询计划和必要索引 → 控制每轮上下文/工具数据量 → 减少重复读取与阻塞调用 → 流式输出改善感知延迟 → 若 SQLite 写竞争或本机多进程确有瓶颈，再评估任务队列/其他数据库。多进程前必须把 `_ACTIVE_RUNS` 和渠道内存账本转为可共享状态；否则取消与去重语义会失效。向量库、消息总线、微服务和容器编排没有当前性能证据，不列为既定实现。

## 参考项目的具体取舍

| 项目源码 | 实际做法 | Nico-agent 取舍 |
|---|---|---|
| Akashic-agent：`E:/Akashic-agent/akashic-agent/agent/tool_runtime.py`、`prompts/agent.py` | 工具结果和提示词行为规则分别组织，并保留执行状态 | **调整后采用**：工具契约和提示词版本独立；不复制人格、后台与主动任务子系统 |
| nanobot：`E:/nanobot/nanobot/agent/loop.py`、`agent/context.py`、`agent/tools/registry.py` | 轮次状态、上下文构造、工具注册分开；提示词引用工具契约 | **采用**清楚的运行/上下文/工具边界；不照搬总线、定时任务和多平台管理器 |
| Pi-agent/pi：`E:/Agent/Pi-agent/pi/packages/agent/src/agent-loop.ts`、`types.ts`、`packages/coding-agent/src/core/system-prompt.ts` | 独立 Agent 循环与协议类型；提示词依据实际可用工具组装 | **调整后采用**运行事件/工具可见性契约；不照搬其 TypeScript monorepo 和编码 Agent 功能 |

三个参考项目的目录规模来自其实际功能和演进历史。它们能证明边界的重要性，不能证明将当前仓库预先拆成多个服务会更快或更好维护。
